Step 2

三个词，三个比喻

记不住 Surface / Component Tree / Data Model 没关系，记住白板、积木、便利贴就行。

1白板 = Surface

一块独立的画布。开个新会话就是换一块白板，多块白板能同时存在，各画各的。

2积木 = Component Tree

白板上摆的东西：卡片、横排、竖排、文字。谁在谁里面，靠 编号互相指。

3便利贴 = Data Model

积木上的字不是写死的，是贴上去的便利贴。换字的时候只换便利贴，不动积木。

积木骨架（只发一次）：  [卡片] → [竖排] → [标签:"assistant"] + [文字: 便利贴 #7]
便利贴（每来一个字发一次）：  #7 = "正在" → #7 = "正在分析" → #7 = "正在分析这个文件…"
Step 3

五种消息 = 五个动作

整个协议只有五种消息，每条消息里只有一种动作。点标签看真实发出去的样子。

beginRendering
surfaceUpdate
dataModelUpdate
interruptRequest
deleteSurface

  


  

    

      
消息人话

      
        
beginRendering换新白板：擦干净，从现在开始画

        
surfaceUpdate摆积木：放上几个、或换掉几个

        
dataModelUpdate换便利贴：只改字，积木一点不动

        
interruptRequest举手问一句：这事要不要做？（人工审批）

        
deleteSurface扔掉整块白板（代码里定义了，但一次都没用过）

      
    

  


  

    技术细节：为什么"一条消息只有一个字段"
    

      
这叫 tag union。每条 JSON 长这样：{"beginRendering": {...}}，五个字段里永远只有一个非空。

      
为什么不用 {"type":"beginRendering","payload":{...}}？因为前端判断能少一层、Go 那边也能少写一个自定义解析器。代价是编译器管不住你——误填两个字段也不会报错，只能靠注释提醒（源码里那句 Exactly one field is populated）。

      
为什么字段都是指针（*BeginRenderingMsg）？因为只有指针的空值 nil 才能让 Go 的 omitempty 真的把字段省略掉；写成普通结构体，即使没内容也会输出 {}，前端就没法区分"没这个动作"和"有这个动作但内容为空"。

对应到代码，就是 TextComp 里的两个字段：

    
// 写死一句话，永远不变 → 用 value
{"Text": {"value": "assistant", "usageHint": "caption"}}

// 以后会一直改 → 只留一位置编号（dataKey），内容走另一条通道
{"Text": {"dataKey": "chat-s1/msg-0", "usageHint": "body"}}


    
一句话：dataKey 就是便利贴上的编号。有编号，才知道该改哪张纸。

  


  
  

    
2为什么所有积木都要带编号

    
看两种存法。切换一下，顺便看"再加一个气泡要重传多少"：

    

      

        
        
      

      
    

    

    


    

      

        带编号的好处
        
想改哪块只发哪块。加一个新气泡，旧的一字不用重传。因为每块积木都能被单独点名。

      

      

        套娃的代价
        
所有东西塞在同一个大 JSON 里，改一个叶子节点得从根到叶子整条路径重发。而且没办法单独点名某一块。

      

    


    

      技术细节：为什么"按编号覆盖"会带来一个副作用
      

        
surfaceUpdate 的动作是"按编号覆盖"，不是"追加"。前端就一句 components[c.id] = c.component。

        
所以想删掉某一块积木——没有这个动作，只能扔整块白板（这就是 deleteSurface 只有整块级别的原因）。

        
所以想往一个容器里再加一个孩子时，必须把那个容器的孩子名单整个重发一遍。这就是我在 Part 1 演示里第 5 步特意标注的那句"注意 root-col 被重新发了一遍"的根源。

      

    

  


  
  

    
3为什么每条消息后面要加个换行

    
服务器是一条一条发的，但网线那头收到的是一整串字符。不加换行，就不知道一句话到哪儿结束：

    
{"beginRendering":{...}}{"dataModelUpdate":{...}}    ← 连成一坨，没法拆

    
加了换行，就像给每句话加个句号。点「开始」看它怎么被拆开：

对应代码就三行，Encode() 最后那个 append(data, '\n') 就是加句号：

    
func Encode(msg Message) ([]byte, error) {
    data, err := json.Marshal(msg)
    if err != nil { return nil, err }
    return append(data, '\n'), nil   // ← 就为这个
}

  







  
Step 5

  
最后：它换来了什么，付出了什么


  

    

      
换来的

      
    
        
  • 界面能被存成文字 → 聊天记录回放、"选中历史会话"都是免费的
    • 
        
  • 手机 App、浏览器、命令行，同一份数据都能画
    • 
        
  • 模型只能填"卡片/文字"，塞不进恶意脚本
    • 
        
  • 打字过程只传字，不传积木 → 省带宽、不闪屏
    • 
      

    

    

      
付出的

      
    
        
  • 没有"删除一块积木"的动作
    • 
        
  • 往容器里加东西时，得把名单整个重发
    • 
        
  • 打字时每次都发累计的全文，长回答会越来越费流量
    • 
        
  • 积木编号是人工约定（msg-0-card 这种），容易写错
    • 
      

    

  


  

    整份 types.go 就一件事：把"界面"拆成「不会变的结构」和「一直在变的字」，分两条通道传。

    理解了这一点，剩下的字段设计全都是这句话的推论。
  


  

    
→这个文件里没用上的东西

    
还有几个字段是"按规范留着位置"的：DeleteSurface 定义了没发过；DataContent 只支持字符串（规范里还有数字/布尔）；usageHint 只实现 caption 和 body 两种。这些都是子集实现，留着以后加。
